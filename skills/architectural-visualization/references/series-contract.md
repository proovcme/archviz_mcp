# Контракт серии и проверка MCP

`visualization_workflow()` возвращает JSON Schema паспорта и границы возможностей. `check_visualization_series(series)` проверяет заполненные записи. Сервер не рендерит, не просматривает изображения, не подтверждает авторство пользовательских цитат, не читает/сохраняет файлы. `can_expand_series` и `can_release_selection` означают полноту согласованных записей, а не автоматическое доказательство фотореализма.

## Заполнение

Паспорт — JSON проекта, например `archviz-series.json`, который сохраняет хост. Не клади его, клиентские изображения или BIM в репозиторий инструмента. Все неизвестные поля отклоняются: используй схему из текущей версии инструмента.

- `project_id`, `goal` (`photographic`/`illustrative`), `execution` (`generative`/`scene_render`), `strict_geometry`.
- `model` и `geometry_sources`: `asset_id` + SHA-256 фактических байтов. Путь сам по себе не обозначает ревизию. Настройки сцены/камеры в JSON хешируй в устойчивой сериализации.
- `appearance_references`: та же идентичность + `origin` и `use_for`. Фотография и принятое сгенерированное изображение — разные происхождения.
- `cameras`: уникальный `camera_id`, хеш настройки/исходника камеры, описание её назначения и известных параметров. Изменение камеры требует нового экспорта.
- `material_brief`, `lighting_brief`, `allowed_changes`: критерии этого проекта.
- Для `scene_render` обязателен `scene_lock` со снимками `scene`, `materials`, `lighting`; кандидаты ссылаются на те же версии. Фактическое исполнение рендера отдельно проверяет хост.
- `candidates`: уникальный ID, снимок изображения, модель, камера, использованные геометрические исходники и при необходимости `scene_lock`.

## Пробный кадр и проверки

1. Добавь кандидата без `review`, задай `pilot_candidate_id`, вызови проверку. В строке кандидата получишь `review_context_sha256`.
2. Открой фактическую картинку и её источники. Заполни `review.context_sha256` этим значением. Для `geometry` и `appearance` укажи `status` (`pass`/`fail`/`not_reviewed`) и конкретные `observations`. Это записи визуального разбора, не результаты скрытого классификатора.
3. Перенеси явную пользовательскую оценку в `feedback`: точный снимок `image`, `author=user`, `decision=accepted/rejected`, `scope=appearance/geometry/overall`, `quote` из диалога. Решение агента записывай с `author=agent`.
4. Перед расширением обе проверки пилота должны пройти, а пользователь — принять именно его подачу. Явное разрешение не ждать сохраняй как `pilot_waiver`; оно отменяет только паузу, не визуальный разбор. Не выдумывай waiver из общего запроса «сделай картинки».
5. Добавь оставшиеся кандидаты и выбери `selected_candidate_ids`. Для многокадрового отбора обязательна проверка `series_consistency` каждого выбранного кадра. Все заявленные камеры покрываются ровно одним выбранным кандидатом.

Замена изображения, модели, камеры, геометрического исходника, целевого материала/света, эталона подачи или ревизии общей сцены делает старый разбор неактуальным. Новую проверку записывай после повторного просмотра, не простым обновлением хеша.

## Отбор и история

Решения относятся к снимку и области оценки; другой файл с тем же именем их не наследует. Пользователь может изменить мнение по той же версии — последнее явное решение в соответствующей области учитывается по порядку записей. Агент не отменяет пользовательское отклонение собственным `accepted`.

Отклонённые варианты могут оставаться в `candidates` для истории, но исключаются из `selected_candidate_ids`. Успешный пилот не означает успешную серию. При строгой геометрии генеративный маршрут не проходит контракт даже с хорошими визуальными оценками.

`test_visualization.py` содержит синтетические паспорта и проход по реальному stdio MCP. Фиктивные хеши тестов не предназначены для проектных записей.
